## 1. 어떤 기능이 어느 단계인가

만드는 순서는 `PHASES/PHASE1~5.md`에서 관리합니다. 이 문서는 **각 기능이 어떻게 동작하는지**만 다룹니다.

| 기능 | PRD 번호 | 단계 |
|---|---|---|
| 소셜 로그인 / 회원 만들기 | F-01 | Phase 1 |
| 명소·작품 정보 (공공데이터 + 관리자 등록) | F-05 | Phase 2 |
| 메인 화면 — 배너, 국적 선택 | F-02 | Phase 2 |
| 검색 (통합 + 드라마·영화 구분) | F-03 | Phase 2 |
| 위치기반 추천 — 비로그인 분기 | F-04 | Phase 2 |
| 명소 상세 + 카카오맵 | F-05 | Phase 2 |
| 즐겨찾기 | F-06 | Phase 3 |
| 리뷰 (별점·글·사진·좋아요·신고) | F-07 | Phase 3 |
| 추천 고도화 — 검색이력 반영 | F-04 | Phase 3 |
| 마이페이지 / 회원탈퇴 | F-10, F-11 | Phase 3 |
| 메인 화면 — 명예의전당, Top10 | F-02 | Phase 3 |
| 코스 추천 | F-08 | Phase 4 |
| 외부 공유 | F-09 | Phase 4 |
| 다국어 번역 · 음역 | N-01 | Phase 4 |
| 배포 (주소 등록, HTTPS) | — | Phase 5 |

### 순서에서 주의할 점 두 가지

**메인 화면이 두 단계로 쪼개져 있습니다.** 명예의전당은 "그 **주(週)** 좋아요가 가장 많은 후기의 대표 사진", Top10은 "즐겨찾기가 가장 많은 명소"입니다. 둘 다 리뷰·즐겨찾기 데이터가 있어야 계산되는데 그건 Phase 3에서 생깁니다. 그래서 Phase 2에서는 배너·국적 선택만 만들고 자리를 비워둡니다. (2026-08-28: 월→주로 변경)

**번역이 Phase 4지만 앞 단계에 숙제를 남깁니다.** Phase 2에서 번역문을 담을 **자리**를 미리 만들고, Phase 3에서 리뷰의 **원래 언어**를 기록해둬야 합니다. 나중에 하려 하면 이미 쌓인 데이터를 갈아엎어야 합니다.

### 아예 만들지 않는 것

지원 언어 확대 · 즐겨찾기 폴더 분류 · 실제 방문 인증 · 탈퇴 전 안내 문구 (전부 PRD에서 "추후 추가"로 남긴 것)

> **주의**: 마이페이지의 "방문 인증한 촬영지 수"는 위의 "실제 방문 인증"과 다릅니다. 별도 인증 절차 없이 **내가 리뷰를 쓴 서로 다른 명소의 개수**를 세어 보여주는 것뿐입니다. (2026-08-28)

## 2. 서버가 보관할 정보

서버를 네 개의 방으로 나눕니다.

| 방 | 보관하는 것 | 따로 두는 이유 |
|---|---|---|
| 회원 | 누가 가입했는지, 국적·언어 | 다른 모든 방이 "누가"를 물어봄 |
| 명소·작품 | 명소, 작품, 둘의 연결, 번역문 | 서비스의 원재료. 관리자만 건드림 |
| 리뷰 | 후기, 별점, 사진, 좋아요, 신고 | 사용자가 만드는 것. 계속 늘어남 |
| 즐겨찾기 | 누가 어떤 명소를 저장했는지 | 하는 일이 단순해서 섞으면 손해 |

검색은 별도의 방이 아니라 **명소·작품 방이 제공하는 기능**입니다. 검색 대상이 명소와 작품뿐이라 따로 뗄 이유가 없습니다.

### 2-1. 회원 방

**보관하는 정보**

| 항목 | 설명 |
|---|---|
| 소셜 계정 식별값 | Google·Kakao가 알려주는 "이 사람이 누구인지" 구분하는 값 |
| 어느 소셜인지 | Google / Kakao |
| 이메일 | 소셜에서 받아옴 |
| 닉네임 | 화면에 보이는 이름. **최대 20자** (2026-08-28, 목업 "3/20") |
| 프로필 사진 URL | 소셜에서 받아옴. 제공 여부는 소셜·사용자 설정에 따라 다를 수 있어 비어있을 수 있다. 사용자가 `PATCH /api/account/`로 직접 바꾸거나 지울 수 있다 — 파일은 서버가 받지 않고, 프론트엔드가 Firebase Storage에 올린 URL만 보낸다(리뷰 사진과 동일, 6-1 #2·#25) (2026-08-28) |
| 국적 | 메인 화면에서 고른 값 |
| 언어 | 국적과 하나로 묶임 (PRD N-01) |
| 약관 동의 시점 | 언제 동의했는지 날짜 |
| 가입일 | |
| 탈퇴 여부 / 탈퇴일 | |

**규칙**

- 전화번호는 받지 않는다. 이메일·비밀번호 방식도 만들지 않는다.
- 가입 시 추가로 물어보는 정보는 없다. 처음 로그인하면 그대로 회원이 된다.
- 국적을 고르지 않은 사람은 한국어를 기본으로 본다.

**탈퇴 처리가 특이합니다**

PRD에 "탈퇴해도 리뷰는 익명으로 남긴다"고 되어 있습니다. 그런데 회원 기록을 통째로 지우면, 그 사람이 쓴 리뷰들이 주인 없는 상태가 되어 같이 사라집니다.

그래서 **회원 칸은 남겨두고, 이름·이메일 같은 개인정보만 비운 뒤 "탈퇴함" 표시**를 합니다.

- 화면에는 작성자가 "탈퇴한 사용자"로 보인다.
- 탈퇴한 사람은 로그인할 수 없다.
- 같은 소셜 계정으로 다시 가입하면 **새 회원**으로 시작한다 (예전 즐겨찾기·리뷰는 돌아오지 않는다).

### 2-2. 명소·작품 방

**명소**

이름 / **설명** / 주소 / 지도상 위치 / 대표 사진 / 영업시간 / **추천 방문 시간 · 사진 팁 · 주의할 점** / 공공데이터 원본 번호(**여러 출처를 가질 수 있음**) / 등록일

> **추천 방문 시간 · 사진 팁 · 주의할 점 (2026-08-28, 6-1 #25)**: 목업·여운 API 명세서(`GET /spots/{spotId}` = `recommendedTime`, `photoTips`, `etiquette`)에 있어 필드를 추가했다. 전부 **관리자 전용**이고, 영업시간과 마찬가지로 **번역하지 않는다**(항상 한국어 원문). 코드에서는 `Place.recommended_time` / `Place.photo_tips` / `Place.etiquette`. `openHours`는 기존 `Place.business_hours`가 그 역할이다.

> **"설명"의 성격 (2026-08-28)**: 목업의 명소 상세에는 "이 장소의 이야기"라는 감성적인 소개 문단이 나옵니다(예: *"1871년, 신미양요의 포성이 울리던 바닷가…"*). 이건 별도 필드가 아니라 **기존 `설명` 필드를 감성적인 톤으로 관리자가 직접 작성**하는 것입니다. 공공데이터의 장소설명 원문을 그대로 넣지 않습니다(`import_kcisa`가 description을 아예 안 가져오는 것과 일치, 6-1 #6).

**작품**

제목 / **설명** / 드라마·영화 구분 / 방영·개봉 시기 / 주연배우 / 감독 / 포스터

> **"설명"의 성격 (2026-08-28, 2026-09-01 수정)**: 작품 상세의 "이 드라마의 이야기"는 원래 `설명` 필드를 감성적인 줄거리 소개로 관리자가 직접 작성하는 것이었습니다. **영화는 KMDB 줄거리로**(6-1 #28), **드라마 등은 TMDB 줄거리로**(6-1 #29) 초기값을 채우고, 관리자가 이후 감성적인 톤으로 다시 쓸 수 있습니다. 먼저 채워진 값이 있으면 다른 소스가 덮어쓰지 않으며, 어느 소스로도 못 채우는 작품은 기존대로 관리자가 처음부터 직접 작성합니다.

**등장 정보 (명소 × 작품)**

"이 명소가 이 작품의 어떤 장면에 나왔다"는 설명.

> **왜 따로 두는가**
> 한 명소에 여러 작품이 찍히고(남산타워에 드라마 여러 편), 한 작품이 여러 명소에서 찍힙니다. 그래서 "명소 안에 작품 넣기"도 "작품 안에 명소 넣기"도 안 되고, 둘을 잇는 자리를 따로 만들어야 합니다.
> 장면 설명은 바로 이 자리에 붙습니다. 같은 남산타워라도 작품마다 나온 장면이 다르기 때문입니다.

**번역문**

명소 이름·설명, 작품 제목·설명을 언어별로 보관합니다. 자세한 규칙은 5장.

**공공데이터 원본 번호를 같이 저장하는 이유**

나중에 공공데이터가 갱신됐을 때 "이건 우리가 이미 가진 그 명소"임을 알아보기 위해서입니다. 이 번호가 없으면 데이터를 다시 받아올 때마다 같은 명소가 중복으로 쌓입니다.

또한 서로 다른 공공데이터 출처가 같은 물리적 장소를 가리키는 경우가 있어서, 명소 하나가 출처를 여러 개(예: 한국문화정보원 + 경기 데이터 드림) 가질 수 있습니다. 두 출처가 같은 장소인지는 좌표 거리(100m 이내)로 판단합니다. 자세한 내용은 7장 #1 참고.

**주변 상권은 저장하지 않습니다**

명소 상세에 주변 상권이 나오지만, 우리가 보관하지 않고 **카카오맵에서 그때그때 받아와 보여줍니다.** 상권은 폐업·신규가 잦아서 우리가 들고 있으면 금방 틀린 정보가 됩니다. 저장 여부는 코스 기능(Phase 4)을 만들 때 다시 판단합니다.

### 2-3. 리뷰 방

| 보관 대상 | 항목 |
|---|---|
| 리뷰 | 누가 / 어떤 명소에 / 별점 / 글(**최대 500자**) / 작성일 / **원래 무슨 언어로 썼는지** / 숨김 여부 |
| 리뷰 사진 | 리뷰 하나에 **최대 5장**. 여러 장이면 **첫 번째 장이 대표 이미지** |
| 리뷰 번역 | 언어별 번역문 (처음 열람될 때 만들어짐) |
| 좋아요 | 누가 어떤 리뷰를 (한 사람이 같은 리뷰에 한 번만) |
| 신고 | 누가 어떤 리뷰를 왜 / 관리자 처리 여부 |

**"원래 무슨 언어로 썼는지"를 저장하는 이유**: 한국인이 한국어로 쓴 리뷰를 한국인에게 보여줄 땐 번역이 필요 없습니다. 원래 언어를 알아야 번역을 건너뛸 수 있습니다.

**좋아요를 리뷰와 함께 만드는 이유**: 명예의전당이 "그 **주** 좋아요가 가장 많은 후기"입니다. 같은 Phase 3 안에서 리뷰를 먼저 만들고 명예의전당을 나중에 채우는데, 리뷰를 만들 때 좋아요를 빠뜨리면 계산할 재료가 없습니다.

**명예의전당에 실제로 나가는 이미지 (2026-08-28)**: "그 주 좋아요가 가장 많은 리뷰"를 고른 뒤, 그 **리뷰의 대표 이미지(사진 중 첫 번째 장)**를 명예의전당 카드에 보여줍니다. 좋아요는 사진 단위가 아니라 **리뷰 단위**입니다. 명소 상세의 사진 갤러리(목업 "오라동 메밀밭 103개")는 그 명소에 달린 리뷰 사진들을 모아 보여주는 화면이고, 각 항목의 하트도 그 사진이 속한 리뷰의 좋아요 수입니다.

### 2-4. 즐겨찾기 방

누가 / 어떤 명소를 / 언제 저장했는지.

같은 사람이 같은 명소를 두 번 저장할 수 없게 막습니다.

### 2-5. 검색 기록

로그인한 사람이 무엇을 검색했는지 남깁니다. 누가 / 무슨 말을 / 언제.

**Phase 2에서 쓰는 곳**: 최근 검색어 표시.
**진짜 목적**: Phase 3의 검색 이력 기반 추천(PRD F-04). Phase 2부터 쌓아두지 않으면 Phase 3을 시작할 때 쓸 데이터가 없습니다.

**추천(인기) 검색어도 여기서 나옵니다 (2026-08-28)**: 목업 검색 홈의 "추천 검색어" 해시태그는 관리자가 고르는 게 아니라 **검색 기록을 집계해 자동 산출**합니다. 구현: `GET /api/search/popular/` — **최근 30일** 검색 기록을 keyword별로 세어 많이 검색된 순 **상위 5개**를 돌려준다. 1회만 검색된 말도 포함한다. 로그인이 필요 없다 (`places/views.py` `PopularKeywordsView`).

> **아직 확인 필요**: 지금 검색 기록은 **로그인한 사람 것만** 남깁니다(위 규칙, 3-2 예외 상황). 인기 검색어를 비로그인 검색까지 반영하려면 익명 검색도 집계용으로 남겨야 하는지 팀과 정해야 합니다. 우선은 로그인 사용자 검색 기록만으로 산출합니다.

## 3. 기능별 상세

### 3-1. 회원

| 할 수 있는 일 | 로그인 |
|---|---|
| Google·Kakao로 로그인 (처음이면 자동 가입) | — |
| 내 정보 보기 | 필요 |
| 닉네임·국적·언어 바꾸기 | 필요 |
| 탈퇴하기 | 필요 |

**규칙**

- 로그인은 Google·Kakao가 대신 확인해준다. 서버는 "이 사람 맞다"는 증표만 받아서 회원을 찾거나 새로 만든다.
- 약관 동의는 가장 첫 화면에서 받고, 동의한 시점을 회원 정보에 남긴다.
- 마이페이지에서 보여줄 것: 프로필 / 즐겨찾기 목록 / 내가 쓴 리뷰 / 국적·언어 설정. (저장한 코스는 Phase 4에서 추가)
- 수정할 수 있는 것: 프로필(닉네임 20자 이내, 프로필 사진 URL — `PATCH /api/account/`), 국적·언어(`PATCH /api/account/locale/`).
- 프로필 상단 활동 요약 두 개 (2026-08-28, 목업). `GET /api/account/` 응답에 포함:
  - **방문 인증한 촬영지 수** (`reviewed_places_count`) = 그 회원이 리뷰를 쓴 서로 다른 명소의 개수 (숨김·삭제된 리뷰 제외). 실제 방문 인증 기능이 아니다.
  - **제안한 코스 수** (`created_courses_count`) = 그 회원이 만든 코스의 개수 (코스는 Phase 4).

**예외 상황**

| 상황 | 어떻게 |
|---|---|
| 증표가 잘못됐거나 만료됨 | 로그인 다시 하도록 안내 |
| 탈퇴한 회원이 로그인 시도 | 새 회원으로 가입 처리 |

### 3-2. 검색 (로그인 불필요)

| 할 수 있는 일 | 설명 |
|---|---|
| 통합검색 | 한 번 검색하면 결과가 **명소 섹션 / 작품 섹션**으로 나뉘어 나옴 |
| 구분 조회 | 작품만, 드라마만, 영화만 골라 보기. 백엔드는 **필터 파라미터만 제공**하고, 이걸 고르는 UI는 프론트엔드가 나중에 붙인다 (2026-08-28, 목업 검색결과 화면엔 아직 탭이 없음) |
| 자동완성 | 글자를 치는 도중 이름 후보를 보여줌 |
| 최근 검색어 | 로그인한 사람은 서버에 남김 |
| 추천(인기) 검색어 | 검색 기록 집계로 자동 산출한 상위 검색어 (2-5 참고) |

**찾는 방식**

- **저장된 번역 이름까지 같이 뒤진다.** 명소 이름을 언어별로 미리 번역해 두었으므로, 외국인이 영어로 `Gyeongbokgung`을 쳐도 영어 이름끼리 바로 비교하면 찾아진다.
- **글자가 비슷하면 잡아준다.** `Gyeongbokgun`처럼 끝글자가 빠지거나 오타가 나도 찾아준다.

> **검색어를 먼저 번역하지 않는 이유**
> 1. 영어 이름이 이미 저장돼 있으므로 굳이 한국어로 되돌릴 필요가 없다.
> 2. 검색은 가장 자주 일어나는 동작이라, 매번 번역하면 느리고 비용이 계속 나간다. 자동완성까지 붙으면 글자 하나 칠 때마다 번역하게 된다.
> 3. `Gyeongbokgung`은 뜻이 있는 말이 아니라 소리를 옮긴 것이라 번역기가 헤맬 수 있다. 우리가 정한 음역 규칙을 번역기가 똑같이 따라준다는 보장이 없다.

**뜻이 비슷한 것까지 찾아주는 기능(예: "궁궐"로 검색하면 경복궁이 나오는 것)은 만들지 않습니다.** 명소마다 "뜻 지문"을 미리 만들어 두는 준비가 따로 필요하고, 결과가 들쭉날쭉합니다. Phase 4에서 번역을 붙인 뒤에 다시 판단합니다.

**예외 상황**

| 상황 | 어떻게 |
|---|---|
| 결과가 하나도 없음 | "검색결과가 존재하지 않습니다" |
| 검색어가 비어 있음 | 검색하지 않음 |
| 비로그인 사용자의 검색어 | 서버에 남기지 않음 (최근 검색어는 프론트가 기기에 보관) |

### 3-3. 명소 상세 (로그인 불필요)

한 화면에 다음이 함께 나갑니다.

- 명소 기본 정보(이름·주소·사진·영업시간) — **보는 사람의 언어로**
- "이 장소의 이야기" — 감성적인 소개 문단 (= `설명` 필드, 2-2 참고)
- 이 명소가 나온 작품 목록 + **작품별 장면 설명**
- 작품 정보 (제목, 방영 시기, 주연배우, 감독)
- 리뷰 목록과 별점 평균 (+ 리뷰 개수)
- 지도 위 위치
- 주변 상권 (카카오맵에서 즉석으로) — 목업에선 "주변 맛집 / 주변 카페 / 함께 방문하면 좋은 촬영지"로 나뉘어 나온다
- 로그인한 사람이면 **내가 이미 즐겨찾기 했는지** 표시

**규칙**

- 길찾기는 우리가 만들지 않고 카카오맵으로 넘긴다.
- 사진은 관리자가 등록한 것과 사용자 리뷰 사진을 함께 보여준다.

> **추가 필드 (2026-08-28, 6-1 #25 → 추가함)**: "추천 방문 시간"(예: *5월, 초저녁*), "사진 팁", "주의할 점"(예: *나무를 꺾지 말아주세요*). 여운 API 명세서에 있어 `Place`에 필드를 추가했다. 관리자 전용, 번역 안 함. 응답 키: `recommended_time` / `photo_tips` / `etiquette`.

**예외 상황**

| 상황 | 어떻게 |
|---|---|
| 없는 명소를 열려고 함 | "존재하지 않습니다" |
| 번역이 아직 승인되지 않음 | 한국어 원문을 보여줌 |
| 리뷰가 하나도 없음 | 빈 목록 (오류 아님) |

### 3-4. 즐겨찾기 (전부 로그인 필요)

| 할 수 있는 일 |
|---|
| 명소 저장하기 |
| 저장 취소하기 |
| 내 저장 목록 보기 |

**규칙**

- 같은 명소를 두 번 저장할 수 없다.
- Phase 3에서는 명소만 저장한다. (코스 저장은 Phase 4)
- 저장 개수 제한, 폴더·태그 분류는 넣지 않는다.

**예외 상황**

| 상황 | 어떻게 |
|---|---|
| 로그인 안 한 사람이 저장 시도 | "로그인이 필요한 기능입니다" |
| 이미 저장한 명소를 또 저장 | 이미 저장된 상태로 처리 (오류 아님) |
| 저장하지 않은 명소를 취소 | 아무 일 없음 (오류 아님) |

### 3-5. 리뷰

| 할 수 있는 일 | 로그인 |
|---|---|
| 명소의 리뷰 목록 보기 | 불필요 |
| 리뷰 쓰기 (별점·글·사진) | 필요 |
| 내 리뷰 고치기·지우기 | 필요 |
| 좋아요 누르기·취소 | 필요 |
| 신고하기 | 필요 |
| 내가 쓴 리뷰 모아보기 | 필요 |

**규칙**

- 한 명소에 리뷰를 여러 개 쓸 수 있다.
- 글은 **최대 500자**, 사진은 **최대 5장**이다 (6-1 #14, 2026-08-28 정정).
- 실제로 방문했는지는 확인하지 않는다. (PRD에서 "추후 추가")
- 리뷰를 쓸 때 어느 언어로 썼는지 함께 기록한다.
- 좋아요는 한 사람이 같은 리뷰에 한 번만.
- 서로 다른 사람이 **5명** 신고하면 그 리뷰는 자동으로 감춰진다 (6-1 #13). 그 외에는 관리자가 확인하고 감춘다. 감춰진 리뷰는 목록에 나오지 않는다.

**예외 상황**

| 상황 | 어떻게 |
|---|---|
| 로그인 없이 쓰기·좋아요·신고 시도 | "로그인이 필요한 기능입니다" |
| 남의 리뷰를 고치거나 지우려 함 | 거부 |
| 이미 지워진 리뷰를 또 지움 | 아무 일 없음 |
| 탈퇴한 사람이 쓴 리뷰 | 작성자 자리에 "탈퇴한 사용자" |
| 같은 리뷰를 여러 번 신고 | 한 사람당 한 번만 접수 |

### 3-6. 관리자가 하는 일

| 순서 | 하는 일 |
|---|---|
| 1 | 공공데이터에서 촬영지 목록을 **가져온다** (버튼 한 번 또는 정해진 주기) |
| 2 | 가져온 명소에 **장면 설명·사진**을 채워 넣는다 (작품 연결은 KCISA는 자동, 나머지는 수동 — 아래 참고) |
| 3 | 채운 글을 **번역하고, 결과를 확인한 뒤 승인**한다 |
| 4 | 신고된 리뷰를 확인하고 감춘다 |

**가져오기 규칙**

- 먼저 공공데이터 원본 번호(출처+원본번호)로 "이미 아는 데이터인지" 판단한다. 있으면 갱신한다.
- 없으면, 좌표(필요하면 카카오 지오코딩으로 얻은 좌표)가 기존 명소와 100m 이내인지 확인해 같은 물리적 장소면 그 명소에 출처만 추가하고, 100m 이내에 아무것도 없으면 새 명소를 만든다.
- 관리자가 직접 채워 넣은 내용(장면 설명, 사진)은 가져오기로 덮어쓰지 않는다. 공들여 채운 것이 사라지면 안 되기 때문이다.
- **한국문화정보원(KCISA) 전용 규칙 (2026-08-29, 6-1 #27)**: 이 CSV는 **미디어타입이 `drama`/`movie`인 행만** 가져온다. `show`(예능)·`artist`(뮤직비디오) 행은 명소(Place)조차 만들지 않는다 — 우리 서비스는 영화·드라마 촬영지라서다. 경복궁처럼 예능·드라마 양쪽에 나오는 장소는 드라마 행이 만들어주므로 목록에서 빠지지 않는다. 가져온 drama/movie 행은 **그 자리에서 작품(Work)을 찾거나 만들어 `PlaceWork`로 잇는다** — 같은 제목(공백 정리 후)이면 같은 작품으로 본다. `PlaceWork.scene_description`은 관리자 몫이라 재수집으로 덮어쓰지 않는다.

**후보 데이터 출처**

명소·작품 데이터를 채울 때 참고할 외부 출처 후보. 전부 그대로 쓰는 게 아니라 **필요한 데이터만 골라서** 쓴다. 어느 것을 실제로 쓸지, 명소·작품 필드에 어떻게 매핑할지는 아직 정하지 않았다 (7장 참고).

| 출처 | 제공 형태 | 주요 항목 | 비고 |
|---|---|---|---|
| 영화진흥위원회(KOBIS) | Open API | 제목, 배우, 감독, 개봉일, 관객수 | 인기 영화 목록 확인 가능. **포스터는 제공하지 않음.** `places/sources/kobis.py` |
| TMDB (The Movie Database) | Open API (v4 토큰) | 줄거리, 감독/연출, 방영·개봉일, **포스터**, 원어 | **드라마 보강에 실제로 씀 (6-1 #29).** KMDB로 못 채운 작품도 커버. `places/sources/tmdb.py` |
| 경기 데이터 드림 | Open API | 시·군명, 작품명, 촬영분류, 년도, 장소 | 경기콘텐츠진흥원이 지원한 촬영지 목록. 명소·작품 연결 정보로 활용 가능 |
| 한국문화정보원 | 공공데이터포털 파일(CSV) — API 제공 여부는 미확인 | 미디어제목, 장소명, 장소설명 | 장소 설명 텍스트 확보 가능 |
| 필름코리아 | 홈페이지 목록 (세트 20여 곳, 로케이션 4,900여 곳) | 세트·로케이션 명 (세트장은 "OOO세트장"으로 표기) | API·CSV 제공 여부 확인 필요. 로케이션 목록 후보로 참고 |
| 한국영상자료원 KMDB | Open API | 제목, 감독, 배우, 줄거리, 개봉일, 포스터 | **영화 보강에 실제로 씀 (6-1 #28).** 제목/감독/키워드로 검색해 영화(Work) 정보를 보강 |

## 4. 번역 규칙

### 4-1. 언제 번역하는가

| 대상 | 시점 | 이유 |
|---|---|---|
| 명소·작품 설명 | 관리자가 등록할 때 미리 | 개수가 적고 거의 안 바뀜. 손님은 즉시 보게 됨 |
| 리뷰 | 누군가 처음 열어볼 때 | 계속 늘어나고 안 읽힐 것도 많음. 한 번 번역하면 저장해서 다음 사람부터는 즉시 |

원래 언어와 보는 사람의 언어가 같으면 번역하지 않습니다.

### 4-2. 고유명사는 음역한다

한국 고유명사는 **뜻을 옮기지 않고 소리 나는 대로** 적습니다.

- `경복궁` → `Gyeongbokgung` (○)
- `경복궁` → `Gyeongbok Palace`, `Scenery Palace` (×)

**이유**: 손님이 현지에서 길을 묻거나 표지판을 찾을 때 실제로 통하는 표기여야 합니다. 뜻으로 옮긴 이름은 한국에서 아무에게도 통하지 않습니다.

음역 대상: 지명과 순우리말. (PRD N-01)

### 4-3. 번역 실패를 어떻게 판단하는가

실패는 두 종류이고, 난이도가 완전히 다릅니다.

**(1) 확실한 실패 — 기계가 판단할 수 있음**

| 기준 | 설명 |
|---|---|
| 답이 안 옴 | 번역 서비스가 오류를 돌려줌 |
| 시간 초과 | 정해둔 시간 안에 안 옴 |
| 빈 값 | 번역 결과가 텅 비어 있음 |
| 원문과 똑같음 | 한국어를 넣었는데 한국어가 그대로 나옴 = 번역이 안 된 것 |
| 길이가 터무니없음 | 원문의 1/5보다 짧거나 5배보다 김 = 잘렸거나 딴소리 |

> **길이 검사는 20자가 넘는 글에만 적용합니다.**
> 짧은 이름에 이 규칙을 쓰면 멀쩡한 번역을 실패로 오해합니다. 한글 한 글자를 소리대로 옮기면 로마자 서너 자가 되기 때문입니다.
> 예: `북촌`(2자) → `Bukchon`(7자)은 3.5배, `청계천`(3자) → `Cheonggyecheon`(14자)은 4.7배입니다. 둘 다 정상인데 5배 기준에 아슬아슬하게 걸립니다. 명소 이름은 거의 다 짧으므로 길이 검사에서 빼야 합니다.

**기다리는 시간은 두 곳이 다릅니다.**

| 대상 | 기다리는 시간 | 이유 |
|---|---|---|
| 명소·작품 | 30초 | 관리자가 미리 하는 일이라 아무도 기다리지 않음 |
| 리뷰 | 5초 | 사람이 화면을 열어놓고 기다리는 중 |

**(2) 애매한 실패 — 기계가 못 잡음**

경복궁을 `Scenery Palace`로 번역해 온 경우입니다. 답은 멀쩡히 왔고 길이도 정상이고 문법도 맞습니다. **기계 입장에서는 성공입니다.** 그런데 우리 서비스의 핵심 규칙을 어겼습니다.

이걸 자동으로 100% 잡는 방법은 없습니다. 그래서 대상에 따라 다르게 막습니다.

| 대상 | 막는 방법 |
|---|---|
| 명소·작품 | **관리자가 눈으로 확인하고 승인해야 손님에게 보인다** |
| 리뷰 | 기계 검사만 하고, 이상하면 신고 기능으로 걸러낸다 |

**명소·작품에 승인 절차를 두는 이유**: 어차피 관리자가 등록할 때 미리 번역하므로 확인할 기회가 있습니다. 명소는 몇 백 개 수준이고 한 번 확인하면 끝이라 감당할 만합니다. 그리고 여기가 음역 규칙이 가장 중요한 곳입니다 — 손님이 길 물어볼 때 쓰는 이름이기 때문입니다.

**리뷰에 승인을 두지 않는 이유**: 계속 늘어나서 사람이 다 볼 수 없습니다. 리뷰는 개인 감상이라 고유명사 오역의 피해도 작습니다.

### 4-4. 실패하면 어떻게 하는가

| 대상 | 처리 |
|---|---|
| 리뷰 | 즉시 원문을 보여준다. 다시 시도하지 않는다(사람이 기다리는 중이므로). 다음에 누가 또 열면 그때 재시도 |
| 명소·작품 | 실패 목록에 남기고, 관리자가 "다시 번역"을 누를 수 있게 한다. **자동 재시도는 하지 않는다** — 실패가 반복되면 비용만 나가기 때문 |

**번역이 없으면 무조건 한국어 원문을 보여줍니다.** 번역은 외부에 맡기는 일이라 언젠가 반드시 실패합니다. 그때 화면이 통째로 안 뜨는 것보다 한국어라도 보이는 편이 훨씬 낫습니다.
