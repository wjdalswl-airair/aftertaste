# PR 작성 워크플로우

현재 브랜치를 PR로 낼 때 쓸 제목과 본문을 정해진 양식으로 초안 작성한다. **`git push`, `gh pr create` 등 실제 명령은 절대 직접 실행하지 않는다** — `commit` skill과 동일하게, 결과물(제목/본문/복붙용 명령어)만 만들어서 보여주고 실제 실행은 항상 사용자가 한다.

## 순서

1. base 브랜치(기본 `master`, 사용자가 다르게 말하면 그걸 따름)와 현재 브랜치를 확인하고, `git log {base}..HEAD --oneline`과 `git diff {base}...HEAD --stat`로 이 PR에 들어갈 전체 변경 범위를 파악한다. 필요하면 개별 커밋/파일 diff도 더 읽는다.
2. 변경 범위 안에 서로 무관한 주제가 섞여 있으면(예: 이번 세션처럼 기능 A 커밋과 별개 기능 B 커밋이 같은 브랜치에 있는 경우), 무리해서 하나의 PR로 합치지 말고 사용자에게 "하나로 낼지, 나눌지" 먼저 확인한다.
3. 이 브랜치가 어떤 Phase에 해당하는지 `docs/PHASES/PHASE*.md`에서 확인한다. 있으면 해당 문서의 "이 단계에서 만드는 것"과 "완료 기준 체크리스트"를 읽어서 본문 내용과 테스트 섹션 체크 여부를 실제 구현/실행 결과와 대조한다.
4. 아래 고정 템플릿으로 제목과 본문을 작성한다.

## 제목 형식

이 저장소 커밋 컨벤션과 동일한 접두사(`feat:`/`fix:`/`refactor:`/`chore:`/`docs:`/`test:`/`style:`)를 쓰고, Phase 번호가 있으면 붙인다.

```
feat: Phase 7 마이페이지·회원탈퇴 구현
```

## 본문 템플릿

```markdown
## 개요
{1~3문장. 어떤 Phase/기능을 왜 구현했는지, 임시 코드(TempXxx 등)를 교체한 거면 그것도 언급}

## 주요 변경사항

### {화면/영역 이름} (`path/to/File.tsx`)
- {무엇을(어떤 API·컴포넌트) 어떻게 바꿨는지, 구체적으로}
- {기존 기능 재사용 vs 신규 연동 구분해서 명시}

### API (`src/api/xxx.ts`)
- {추가/변경한 함수 이름과 역할}

### 기타
- {위 분류에 안 들어가는 신규 파일/유틸 등}

## BE 확인 필요 (있을 때만 포함)
- {BE 쪽에 후속 확인·개선이 필요한 항목 + 왜 필요한지 한 줄 이유. 별도 이슈로 정리할 거면 그것도 언급}

## 테스트
- [ ] `npm run lint`
- [ ] `npm run build`
- [ ] `npm run test` ({N}개)
- [ ] {브라우저에서 직접 확인한 시나리오가 있으면 구체적으로}
- 확인 못한 것: {예: 로그인 필요한 흐름은 브라우저 직접 확인 못함 — 있는 그대로 정직하게 적는다, 없으면 이 줄 생략}
```

- "BE 확인 필요" 섹션은 실제로 발견한 이슈가 있을 때만 넣는다. 없는데 억지로 채우지 않는다.
- 테스트 체크박스는 이번 세션에서 실제로 돌려보고 통과를 확인한 항목만 `[x]`로 표시한다. 안 돌려봤거나 결과를 못 본 건 `[ ]`로 비워두고 "확인 못한 것"에 정직하게 적는다 — 실제로 안 한 걸 했다고 표시하지 않는다.

## 최종 출력

1. 위 템플릿으로 완성한 제목/본문을 마크다운으로 그대로 보여준다.
2. 사용자가 바로 복붙해서 실행할 수 있도록, 아래 형태의 `gh pr create` 명령어도 함께 보여준다(실행은 하지 않는다):

```bash
gh pr create --title "{제목}" --body "$(cat <<'EOF'
{본문 전체}
EOF
)"
```

## 하지 않는 것

- `git push`, `gh pr create`, `gh pr edit` 등 실제 명령 실행 (사용자 담당)
- 테스트 안 해본 항목을 체크된 것처럼 표시
- 여러 무관한 주제를 사용자 확인 없이 하나의 PR로 합치기
