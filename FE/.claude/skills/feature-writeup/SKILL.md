# 기능 구현 회고 문서화

방금(또는 최근 세션에서) 구현한 기능의 "생각의 흐름"을 나중에 다시 참고할 수 있게 문서로 남긴다. 같은 고민을 다음에 또 처음부터 반복하지 않는 게 목적이다 — 코드만 보면 "무엇을" 했는지는 알 수 있지만 "왜 그렇게" 했는지, 어떤 대안을 버렸는지는 코드에 안 남기 때문이다.

## 정리할 4가지

1. **목적** — 왜 이 기능이 필요했는가. 사용자가 어떤 문제/요청에서 시작했는지, 배경.
2. **기능 선택 이유** — 여러 방법을 검토했다면 각각 무엇이었고, 왜 그중 하나를 골랐는지. 버린 대안(다른 구현 방식, 검토했지만 안 쓴 라이브러리 등)과 그 이유를 반드시 포함한다 — "안 쓴 이유"가 나중에 똑같은 대안을 또 검토하는 시간을 아껴준다.
3. **구현 방법** — 실제로 어떻게 만들었는지. 한 번에 정착하지 않고 시행착오를 거쳤다면(1차 시도 → 한계 발견 → 2차 시도) 그 순서대로 적는다. 핵심 코드 구조나 데이터 흐름을 짧게 포함한다.
4. **해결한 문제** — "문제 → 해결"을 표나 목록으로 짧게 정리한다.

## 순서

1. 이번에 구현한 기능과 관련된 대화·코드 변경을 훑어서 위 4가지 내용을 재구성한다. 없는 내용을 지어내지 않는다 — 실제로 논의·시도한 것만 적는다.
2. `FE/docs/`에 새 마크다운 파일로 저장한다. 파일명은 이 저장소 컨벤션대로 `UPPER_SNAKE_CASE.md`(예: `MASONRY_LAYOUT.md`)로, 기능을 알아볼 수 있는 이름을 쓴다.
3. 관련된 기존 문서(주로 `docs/DETAIL_SPEC.md`의 해당 화면·기능 항목)에 이 새 문서로 가는 링크를 한 줄 추가한다 — 문서가 여기저기 흩어지지 않고 서로 찾아갈 수 있게.
4. 장황하게 쓰지 않는다. 코드 주석으로 충분히 설명되는 "무엇을" 부분은 반복하지 말고, 문서에는 코드에 안 남는 "왜"에 집중한다.

## 예시

`FE/docs/MASONRY_LAYOUT.md` — 리뷰 피드를 핀터레스트식 매스너리로 만든 과정을 이 형식으로 정리한 문서. 목적/기능 선택 이유(CSS `columns-2` 1차 시도 → 페이지네이션 재배치 문제 발견 → 인덱스 기반 2칸 고정으로 전환, 검토했지만 안 쓴 라이브러리)/구현 방법/해결한 문제 순서로 되어 있다. 새로 문서를 쓸 때 이 구조를 참고한다.
