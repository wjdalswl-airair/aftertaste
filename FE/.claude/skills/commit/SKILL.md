# 커밋 워크플로우

세션에서 쌓인 작업을 "작업 내용별로" 나눠서 커밋 준비를 한다. **`git add`, `git commit` 명령은 절대 직접 실행하지 않는다** — 파일 목록과 커밋 메시지를 추천하고, 실제 명령 실행은 항상 사용자가 한다.

## 순서

1. `git status`, `git diff`로 지금까지 쌓인 변경 사항을 전부 파악한다.
2. 변경 사항을 **작업(주제) 단위**로 묶는다. 한 번에 하나의 큰 커밋으로 몰아넣지 않는다 (예: "리디자인"과 "새 기능 추가"는 분리).
3. 같은 파일 안에 서로 다른 작업이 섞여 있으면:
   - 분리 비용이 낮으면(몇 줄짜리 diff) Edit로 해당 부분만 잠깐 되돌려서 먼저 커밋할 그룹만 남기고, 사용자가 그 커밋을 마친 뒤 다시 복원해서 다음 그룹을 준비한다.
   - 분리 비용이 크면(레이아웃/로직이 깊게 얽힘) 무리해서 쪼개지 말고 하나의 커밋으로 묶되, 왜 같이 묶었는지 한 줄로 설명한다.
4. 각 커밋 그룹을 스테이징했다고 가정한 상태에서 `npm run lint` / `npm run build` / `npm run test`가 통과하는지 확인한다 (가능한 경우). 임시로 되돌린 코드(예: 목업 데이터, TEMP 주석)가 섞여 있으면 커밋 전에 반드시 원래대로 되돌려놓는다.
5. 이 프로젝트와 무관한 변경(예: `../BE` 아래 파일)은 커밋 목록에서 제외하고, 제외했다는 사실을 알려준다.
6. 각 커밋마다 아래 형식으로 출력한다:
   - `git add <파일 목록>` (코드 블록, 그대로 복사해서 쓸 수 있게)
   - 커밋 메시지 (코드 블록, 한국어, 이 저장소의 기존 컨벤션을 따름 — `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`, `style:` 등 접두사 + 한 줄 요약). **사용자는 커밋 타이틀(한 줄)만 남기고 본문 불릿은 안 쓴다** — 그래서 불릿으로 상세 내용을 늘어놓지 말고, 제목 한 줄 자체에 무엇을(어떤 화면/컴포넌트/API) 어떻게 바꿨는지 구체적으로 담는다. 필요하면 제목이 길어져도 된다.
7. 커밋이 여러 개라 순서대로 진행해야 하면, 사용자가 한 커밋을 마칠 때까지 기다렸다가("~했어" 같은 확인을 받으면) 다음 커밋을 위해 필요한 파일 복원 등을 진행한다. 한 번에 모든 걸 다 해놓고 기다리지 않는다.

## 하지 않는 것

- `git add`, `git commit`, `git push` 등 실제 git 명령 실행 (사용자 담당)
- 요청받지 않았는데 `git commit --amend`나 `--force` 사용
- 커밋 그룹을 지나치게 잘게 쪼개서(파일 하나당 커밋 등) 사용자에게 불필요한 반복 작업을 시키는 것 — 의미 있는 작업 단위로만 나눈다
